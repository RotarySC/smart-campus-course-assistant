# 方向 B · 响应式规范 v1

适用对象：`design/responsive/b-responsive.html`（响应式原型）与 `design/responsive/rb.css`（样式契约）。
方向基线：**方向 B「纸感墨绿 · 专注对话」** —— 无侧栏、单列、低密度、暖中性、墨绿主色。
上游依据：`docs/校园课程智能助手_SRS_v0.1.md` NFR-COMP-001（至少覆盖 1366×768 桌面与 390×844 窄屏，
复杂后台表格可在窄屏横向滚动）、NFR-UX-001、WCAG 2.2 AA（含 1.4.10 Reflow）。
本轮修正依据：`design/reviews/render-verification-round2.md`。

---

## 1. 断点系统

mobile-first，**只有 5 档**，全部用 `min-width`。组件里不得出现临时断点。

| 档位 | 区间 | 典型设备 | 本档要保证的事 |
| --- | --- | --- | --- |
| base | `< 480` | 小手机（最窄按 **320px** 验收） | 单列、底部标签栏、表格卡片化、触控目标 ≥44px、**页面零横向滚动** |
| XS | `≥ 480` | 大手机 | 对话气泡限宽 88%、过程区由折叠转为常显 |
| SM | `≥ 768` | 平板 / 窄桌面 | **顶栏内联导航取代底部标签栏**、表格恢复表头、表单两列 |
| MD | `≥ 1024` | 桌面 | 内容与留白达到设计密度 |
| LG | `≥ 1200` | 宽屏 | 达到内容最大宽（880px / 助手 720px），不再变宽 |
| XL | `≥ 1440` | 超宽屏 | 仅增加左右留白，不放大字号、不加宽内容 |

**验收尺寸（必须实测）**：320 / 390 / 768 / 1024 / 1366 / 1440。
其中 390×844 与 1366×768 是 SRS 明确要求的两个尺寸。

**为什么 `768` 是主分界线**：它同时承担三件事——导航换形态、表格↔卡片、表单列数。
把三个变化压在同一个断点，是刻意的：避免出现「窄屏但仍是表格」这类中间态，减少需要验证的组合数。

## 2. 布局规则

| 项 | base–XS（<768） | SM（≥768） | MD–XL |
| --- | --- | --- | --- |
| 页面外边距 | 18px（`--sp-3`） | 24px（`--sp-4`） | 24px |
| 内容最大宽 | 100% | 100% | 880px（`--w-content`）居中 |
| 助手主区最大宽 | 100% | 100% | 720px（`--w-assistant`）居中 |
| 正文 measure | 自然宽度 | 自然宽度 | ≤68ch |
| 纵向节奏 | 24px 起（`--sp-4`） | 36px（`--sp-6`） | 36px |
| 表单列数 | 1 | 2 | 2 |
| 并排卡片 | 堆叠 | 2 列（`.card-row--2`） | 2 列 |
| 底部预留 | 标签栏 56px + `safe-area-inset-bottom` | 0 | 0 |

**不引入侧栏、不引入抽屉式导航。** 方向 B 的身份就是「无侧栏、内容居中单列」；
4 个一级入口在窄屏用底部标签栏承载，比汉堡菜单更省一次点击，也符合移动端惯例（底部导航 ≤5 项）。
<cite>Sidebar / drawer 在本方向被显式否决，属方向身份而非遗漏。</cite>

## 3. 导航形态

| 断点 | 顶栏内联导航（`.appbar__nav`） | 底部标签栏（`.tabbar`） |
| --- | --- | --- |
| `< 768` | `display:none` | `display:grid`，4 项，图标 + 文字，每项高 ≥56px |
| `≥ 768` | `display:flex` | `display:none` |

- 当前项用 `aria-current="page"`：顶栏用**底色 + 加粗 + 主色**三重表达，标签栏用**主色 + 加粗**。
- 顶栏在 `≥768` 才出现导航，因此**不会**出现 Round 2 在评审页上观察到的
  「中等宽度下顶栏控件被挤成竖排文字」——产品导航只有 4 项，且 `≥1200` 前不追加任何右侧控件。
- 顶栏与标签栏都是 `position:sticky/fixed`：**必须为主内容预留占位**（`body` 的 `padding-bottom`
  已含标签栏高度 + 安全区），避免内容被固定栏遮住；键盘焦点同样不得被遮挡（WCAG 2.2 2.4.11）。

> 实际是 `.kv{grid-template-columns:1fr}` 容器 + `.kv__row{grid-template-columns:8em 1fr}`，

## 5. 表格 → 卡片的判定规则

这是本方向唯一需要「同 markup 双形态」的组件，规则必须写死，避免各页各写一套。

**决策规则**
1. 数据是**同构多行 + 字段名固定**的列表 → 用 `.table`。
2. 该列表在 `<768` 下**不允许**出现页面级横向滚动 → `.table` 必须同时加 `.table--stack`，
   并用 `.table-wrap` 包裹（`≥768` 时提供表格自身的横向滚动兜底）。
3. 每张 `.table--stack` 的**每个 `<td>` 都必须写 `data-label="字段名"`**。
   窄屏下 `td::before` 用这个属性渲染字段名；漏写就会渲染出**空字段名**。
   （`build.py` 会在构建期检查并报错。）
4. 超宽表格（如文档 Token 表这类**文档性**表格）允许保留横向滚动，不卡片化——
   SRS NFR-COMP-001 明确允许，但**必须是表格自己滚动，不是页面滚动**。

> **⚠ 「页面级横向溢出 = 0」这个核心验收点的前提**
> 它成立完全依赖一条机制：**超宽内容必须被 `.table-wrap{overflow-x:auto}` 或 `table--stack` 卡片化消化掉**，
> 而不是让内容把页面撑宽。
> 反例路径就写在本文件里：`<768` 的 `.table-wrap--stackable{overflow-x:visible}` ——
> 它刻意取消了表格自己的滚动容器，此时宽度**只能**靠 `table--stack` 卡片化来消化。
> 也就是说：**如果后续有人删掉 `table--stack` 或把 `overflow-x:auto` 去掉，同一处会立刻变成页面级溢出**。
> 实测中最接近临界的是 **S09 学习计划表：767–899px 区间有 25–57px 的内部滚动**（768 下 57px），
> 目前封闭在 `.table-wrap` 内、页面级仍为 0，判定为可接受；但它是这条前提的活例证，改动该区域时必须重测。

**窄屏卡片形态**：`thead` 隐藏；`tr` 成为一张卡；`td` 变 `grid` 两列（字段名 7.5em + 值）；
首列（`.cell-name`）例外，作为卡片标题独占一行、字号升到 17px。

**列宽陷阱（Round 2 实测教训）**
- 不要用 `overflow-wrap: anywhere` 处理表格单元格文本：它会**降低 min-content 宽度**，
  在 `table-layout:auto` 下让该列被压到约 1 个字符宽（另一方向在同类表格上真实发生过）。
- 表格单元格一律 `.cell-name{overflow-wrap:break-word; min-width:180px}`；
  `anywhere` 只用于非表格的长文本容器。
- 固定列宽之和**不得**逼得弹性列无空间：若固定列合计接近容器宽，必须给弹性列 `min-width`，
  让表格整体超出容器并由 `.table-wrap` 横向滚动，而不是把弹性列压塌。

## 6. 排版、密度与触控

| 项 | 值 | 说明 |
| --- | --- | --- |
| 正文字号 | 17px | `--fs-17`。窄屏**不缩小**（≥16px 可避免 iOS 自动缩放） |
| 正文行高 | 1.75 | `--lh-body`，低密度方向的核心手感 |
| 字阶 | 13 / 15 / 17 / 20 / 24 / 32 | 不新增中间字号 |
| 间距基准 | 6px | `--sp-1:6` 起，刻意避开 4 的倍数（方向身份） |
| 圆角 | 卡片 14 / 控件 10 / 胶囊 999 | |
| 阴影 | `0 1px 1px rgba(28,25,23,.04)` | 极淡；层次主要靠留白与 1px 暖色分隔线 |
| 最小触控目标 | 44×44px | `.btn`/`.input`/`a.chip` 的 `min-height:44px`；标签栏项 ≥56px |
| 数字 | `font-variant-numeric: tabular-nums` | 时间、编号、日期不跳动 |

**间距不随断点线性放大**：窄屏到宽屏只调页面外边距（18→24px），组件内部间距保持不变，
这样组件在任何宽度下的手感一致，也减少了「某个宽度下才错位」的验证组合。

## 7. 无障碍与响应式

- **Reflow（WCAG 1.4.10）**：320px 宽、400% 缩放下不得出现**双向**滚动；本方向的验收口径是
  `documentElement.scrollWidth − clientWidth = 0`（六个宽度实测）。
- **文本缩放 200%**：使用相对单位与 `-webkit-text-size-adjust:100%`，不锁定字号。
- **焦点不被遮挡（WCAG 2.2 2.4.11）**：吸底的 `.composer` 与固定的 `.tabbar` 均预留占位；
  跳转链接 `.skip-link` 在聚焦时可见。
- **状态不靠颜色单独表达**：所有状态胶囊都是「内联 SVG 图标 + 文字 + 颜色」；空状态两态
  除颜色外还有不同的插画、标题与动作。
- **动效降级**：仅步骤条进行中图标旋转；`prefers-reduced-motion: reduce` 下全部关闭。
- **表单**：每个控件都有可见 `<label for>`；错误在字段下方且 `aria-describedby` 关联；
  多错时给出 `.error-summary` 并可聚焦。
- **安全区**：底部标签栏与吸底输入区都叠加 `env(safe-area-inset-bottom)`。

## 8. 明确的取舍（不做什么）

| 不做 | 原因 |
| --- | --- |
| 侧栏 / 抽屉式主导航 | 违背方向 B「无侧栏、单列专注」的身份；4 项用底部标签栏足够 |
| 暗色模式 | 上游 PPT/SRS 未要求；B 的暖纸感身份建立在浅底上 |
| 响应式图片 / 懒加载 | 原型零位图，全部内联 SVG；产品化后按实际素材再定 |
| 容器查询（`@container`） | 组件复用场景尚不存在，先用 5 档全局断点，避免过早引入两套响应式模型 |
| 在组件里写临时断点 | 会把需要验证的宽度组合数从 6 个放大到不可控 |

## 9. 验收清单（可直接测）

1. 320 / 390 / 768 / 1024 / 1366 / 1440 六个宽度下，`documentElement.scrollWidth − clientWidth = 0`。
   **前提**：超宽内容须由 `.table-wrap{overflow-x:auto}` 或 `table--stack` 卡片化消化（见 §5 的⚠）。
2. `<768` 出现底部标签栏且顶栏内联导航 `display:none`；`≥768` 相反。
3. `<768` 下 `.table--stack` 的 `thead` 为 `display:none`、`tr/td` 为 `block`，且页面不横向滚动；
   每张 stack 表格的 `<td>` 都有非空 `data-label`。
4. `<768` 下 `.btn` / `a.chip` 高度 ≥44px，`.tabbar__item` ≥56px。
5. 每个 `input/select/textarea` 都有非空可访问名称；装饰性 SVG 带 `aria-hidden="true"`。
6. `performance.getEntriesByType('resource')` 返回空数组（零子资源、零外部请求）。
7. 390px 与 1366px 各截图并**人工看图**：无重叠、无裁切、无压塌列、无错位。
8. content-spec 中的坏消息文案逐字一致（S05 三条、S08 两条、S11 五态与整批规则）。
9. 片段用到的 class 全部能在 `rb.css` 找到定义（`build.py` 构建期检查）。
10. 业务错误码全部落在 SRS §8 / OpenAPI 允许集合内，无自造码。
