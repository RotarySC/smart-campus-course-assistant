S00

设计理由与取舍 · 方向 B「纸感专注 · 对话优先」

评审对照入口：内容与状态冻结清单 v1（三方向共用）。本页所有屏幕块与文案与 A/C 方向逐字一致，差异只在配色、字体、间距密度、圆角阴影与信息组织。

一句话定位

把助手当成唯一主角：安静、低密度、大留白，学生第一次打开就知道「查课表 · 问资料 · 存计划」都在这一个输入框里发生；一切过程反馈都内联在对话流里，不占用右侧面板。

适用场景

  • 学生的日常主流程：一句话查课 → 追问资料依据 → 生成并保存计划。
  • 移动优先 / 窄屏与单手使用；顶栏收纳全部导航，390px 下不需要侧栏折叠。
  • 阅读强度高的场景：资料片段、课程规定原文需要被认真读完，而不是扫一眼。
  • 需要「依据可核对」的信任场景：引用就在回答气泡下方展开，阅读路径零跳转。

不适用场景

  • 管理员在宽屏做批量数据核对：一屏可见行数明显少于方向 A/C。
  • 需要左右并列比对（如 5 种文档状态 + 批次规则 + 错误原因同屏）。
  • 高频重复录入为主的岗位，操作步数被大留白与 44px 触控目标放大。
  • 需要概览仪表盘、密度型监控面板的场合。

优点

  • 助手与输入框是唯一视觉重心，学生主流程几乎不会被导航分心。
  • 过程反馈内联为步骤条，回答、依据、草稿三者在同一阅读轴上，无需在面板间来回看。
  • 「未保存」用琥珀色便签纸（虚线边框 + 纸纹）表达，与成功/失败色完全分离，坏消息不易误读。
  • 暖纸底 + 1px 暖色分隔线 + 极淡阴影，长时间阅读疲劳更低。
  • 390px 下几乎不需要降级改造：本身就是单列 + 吸底输入。

代价

  • 信息密度低是主要代价：管理后台一屏能看的记录数约为紧凑型方向的一半。
  • 为补偿这一点，本方向额外定义「紧凑变体」（行高 40px / 正文 14px）并只用于 S10、S11；S09 学生侧表格仍走标准密度。
  • 无侧栏使管理入口层级更深：需点开顶栏「管理」下拉，二级导航不可常驻。
  • 68ch 正文 measure 在宽屏下会留出大量空白，靠留白而不是靠内容填满，容易被误判为「没做完」。
  • 过程反馈内联会拉长对话滚动长度，长任务需要靠折叠摘要控制高度。

评审提问的五项自答

  1. 第一次打开就知道能干什么吗？是：S02 首屏即标题 + 能力说明 + 三个示例入口，且示例只填入不自动提交。
  2. 5 个坏消息一眼可分吗？是：空结果（虚线中性）/ 读取失败（危险红实线）/ 依据不足（琥珀）/ 检索失败（危险红 + 重试主按钮）/ 待确认（琥珀 + 沙漏，与「已保存」的成功绿+对勾分离），见 S05、S08、S06。
  3. 一屏能否看清 5 种文档状态与整批发布规则？本方向不能完全一屏看清——这正是低密度的代价；S11 改用紧凑变体（40px 行高）把批次头 + 5 行文件 + 整批回滚提示压到尽量近，但仍需滚动。
  4. 390px 下主流程顺畅吗？是：S13 三块模拟显示助手单列 + 过程折叠一行 + 输入吸底，课表为卡片列表无横向滚动。
  5. 代价与不适用场景？见上「代价 / 不适用场景」，并在 S14 后「取舍总结」再次明确。

无障碍落实点（S01）

  • 可见 label：账号 / 密码均为真实 <label for>，未使用 placeholder 充当标签；必填以文字「必填」标记。
  • :focus-visible：3px 墨绿轮廓 + 2px 偏移；scroll-margin-top 保证不被 64px 粘性顶栏遮挡。
  • 错误就近：字段错误在字段下方并通过 aria-describedby 关联，同时顶部摘要 role="alert"。
  • 统一文案：不区分「账号不存在」与「密码错误」，两处文案一致。

取舍

方向 B 的取舍总结（优点 / 代价 / 不适用场景）

本节不引入任何新屏幕块，只做评审结论。

优点

  • 助手是唯一主角：学生主流程（查课 → 问资料 → 存计划）在一个输入框和一条阅读轴内完成。
  • 过程反馈内联为对话内步骤条，与回答、引用、草稿同轴，不需要在「对话区 / 右侧面板」之间来回扫视。
  • 坏消息语义靠形状与色彩双重分离：空=虚线中性、失败=危险红、依据不足=琥珀、待确认=琥珀沙漏，成功绿只留给真成功。
  • 琥珀色被严格限制在「未保存 / 待确认」，因此「便签纸草稿」不会与成功态混淆。
  • 阅读舒适：17px / 1.75 行高 / 68ch measure，长时间看资料片段与课程规定原文更省力。
  • 移动优先天然成立：390px 几乎不需要降级改造，输入吸底、卡片列表、示例横滑即可。

代价

  • 低密度对管理后台效率的影响（本方向最大代价）：标准密度下表格行高约 60–64px、正文 17px，1366×768 一屏只能看到约 7–8 行；同一份文档批次（批次头 + 5 行文件 + 整批回滚提示）在方向 A/C 可能一屏看完，本方向必须滚动。
  • 为此额外定义「紧凑变体」（行高 40px、正文 14px）并强制用于 S10 / S11，把可见行数拉回到约 12 行；但 14px 正文已接近可读下限，且行高 40px 使 44px 触控目标无法落进表格行内，表格内操作只能退到 32px 的次级按钮/图标按钮。
  • 即便使用紧凑变体，S11 的 5 种文件状态 + 批次发布规则仍无法在 1366×768 一屏内全部看清，需要滚动核对——这是低密度方向的固有上限。
  • 删除与停用等危险操作在低密度下更依赖滚动后的二次确认面板，减少了误触，但增加了操作步数。
  • 无侧栏使管理入口层级更深：必须点开顶栏「管理」下拉，二级导航不能常驻、无法一眼看到全部管理模块。
  • 大留白在宽屏上会显得「没做完」，评审时容易被误判为未完成稿。

不适用场景

  • 管理员以宽屏批量核对为主的日常（一次要比对多行、多状态、多错误原因）。
  • 需要并排比对或仪表盘概览的场合（如批次与批次之间、课程与课表之间）。
  • 高吞吐录入场景：大留白与 44px 触控目标会放大操作步数与滚动量。
  • 需要常驻导航树、多模块频繁切换的后台工作台。

结论：方向 B 适合作为学生端的主体验；管理后台若采用它，应接受更低的信息密度，或按本稿方案只在后台局部使用紧凑变体，并把后台的批量核对能力明确列为取舍外能力。
