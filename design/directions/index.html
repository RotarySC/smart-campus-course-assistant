校园课程智能助手 · 前端 UI/UX 方向稿

这是方向稿，不是最终设计。三个方向在内容与状态上完全相同 （同一份 content-spec 冻结了 15 个屏幕块、逐字文案与无障碍硬要求）， 只在配色、字体密度、布局结构与信息组织方式上不同 —— 所以你要比较的是"观感与密度"， 而不是"内容多少"。看完请选一个方向，我再按你选的深度继续。

一、三个方向，一句话各自是什么

A · 学院蓝

清晰秩序

正式、可信、低学习成本。学生与管理员共用一套视觉语言，最接近"学校官方系统的现代化版本"。

  • 主色 #1D4ED8 靛蓝
  • 正文 15px / 行高 1.6 / 间距 4px 基准
  • 左侧栏 240px + 顶栏 56px；助手页三栏（对话 + 右侧 320px 过程面板）
  • 卡片圆角 10px，轻阴影分层
  • 引用用青绿左边框卡片；状态统一为「图标+文字+12% 底色」胶囊

代价：视觉偏正统、个性弱；1366px 下右侧面板需可折叠。

打开方向 A 完整稿

B · 纸感墨绿

专注对话

安静、专注、把助手当唯一主角。低密度大留白，移动优先，学生日常使用最舒服。

  • 主色 #14665B 墨绿；琥珀专用于「未保存/待确认」
  • 正文 17px / 行高 1.75 / 间距 6px 基准（刻意避开 4 的倍数）
  • 无侧栏：单列居中 880px，导航收进顶栏 64px
  • 卡片圆角 14px，阴影极淡；层次靠留白与 1px 暖色分隔线
  • 过程反馈内联为对话内步骤条；草稿卡做成「便签纸」

代价：标准密度下一屏仅 7–8 行，管理后台效率低；已额外定义「紧凑变体」补偿，但 S11 五状态仍无法一屏看清。

打开方向 B 完整稿

C · 深色控制台

数据密集

一屏看完、键盘优先、状态可追溯。管理员与重度用户效率最高，学生看到的是"今日一屏"。

  • 主色 #4F46E5；深色顶栏 #0B1220
  • 正文 13.5px / 行高 1.45 / 间距 2px 基准
  • 可折叠侧栏 216px + 深色顶栏 48px；12 栅格，max-width 1600px
  • 无阴影，一律 1px 边框分层；圆角 6px；表格行高 36px
  • 过程区是右侧 「执行事件流」表格（seq / 时间 / 事件 / 状态）；引用走右侧抽屉

代价：对非技术学生有门槛感；13.5px 在手机上偏小，窄屏需回到 15px 并放弃表格。

三、三个方向都必须满足的硬约束（不是可选项）

这些来自 docs 的契约，三个方向都已实现，换方向也不会变：

  • 空结果 ≠ 读取失败：S08 的两个状态必须并列且视觉可区分，不得合并成"暂无数据"。
  • 五类"坏消息"一眼可分：当天无安排 / 课表读取失败 / 依据不足 / 检索失败 / 写入待确认。
  • 过程区只展示可核实动作（正在读取课表 / 正在检索课程资料 / 正在拟定计划草稿），绝不出现"正在思考"或模型推理。
  • 引用只能来自本次真实检索，且未校验的引用标记必须与已验证引用视觉可区分。
  • 草稿默认「未保存」，保存后必须能给出计划编号并打开；写入结果未知时显示"待确认"而不是失败。
  • 文档批次整批可见或整批不可见，五种文件状态（可检索/处理中/失败/删除中/删除失败）都要能表达失败原因。
  • 状态不靠颜色单独表达：一律"图标 + 文字 + 颜色"三重；可见 label、:focus-visible、prefers-reduced-motion 全在位。
  • 会话是临时的：令牌只存内存、2 小时不续期、刷新需重登 —— 所以助手对话刻意不进 URL。

四、信息架构草图

打开信息架构草图 →

方向无关，三个方向共用。含 7 个部分：

  1. 站点地图（登录 → 四个一级页面 → 管理中心四模块，每节点标 API 端点）
  2. 路由与守卫表（13 行）+ 深链冲突专项 + 未登录/越权统一处理
  3. 导航模型（三级分层、当前项高亮、角色决定菜单、桌面与 390px 双形态）
  4. 四条关键流程（查课表 / 资料问答 / 生成并保存计划 / 管理员批量入库）
  5. 对话请求生命周期（accepted → running → succeeded/failed/cancelled + 断线分支）
  6. 状态 → UI 呈现总表（30 行：HTTP 状态 × 业务错误码 → 页内提示/字段错误/引用失效/胶囊/抽屉/整页）
  7. 会话生命周期（2h 不续期、令牌仅内存、刷新重登、切号清空、清空对话不删计划、禁用即时失效）
一个需要你知道的设计取舍：助手对话为什么不进 URL

通用准则是"URL 应反映当前状态，便于分享与回退"。本项目中 /schedule?date=、 /plans/:id、各管理页都遵守它；但 conversation_id / draft_id / request_id 刻意不写进地址栏。理由：会话只存在当前标签页内存里，刷新即失效； 写进 URL 等于向用户承诺一个不存在的恢复能力 —— 刷新后地址还在但内容已不可恢复，比"URL 不反映状态"更糟。 判据一句话：URL 里出现的东西，刷新后必须仍然成立。 留存诉求改为转移到"显式保存 → plan_id → 可深链的 /plans/:id"。

六、看完请给我一个决定

你只要回答两件事，我就能继续：

  1. 选哪个方向（A / B / C，也可以说"A 的配色 + C 的密度"这种组合）。
  2. 要什么深度：
    • 只要设计文档与规格（设计系统 token、组件规格、页面与状态规格、无障碍与响应式规范、前端技术方案）
    • 文档 + 可点击高保真原型（在选定方向上把 15 个屏幕块做成可交互流程）
    • 文档 + 原型 + Vue 3 可运行骨架（Vue3 + TS + Pinia，落地 token / 布局壳 / 路由 / 主要页面，mock 数据，不接真实后端）

我的建议：方向 A 作为基线，吸收 C 的 S11 文档状态密度与事件可追溯性。 理由是 A 与知识库对"教育/知识库类工具"的独立推荐一致（中性灰 + 链接蓝、Swiss 极简、高可读性）， 风险最低、学生与管理员共用一套语言；而 C 在"一屏确认 5 种文档状态"和"执行事件可追溯"上明显更强， 恰好对应本项目最难的验收点。B 的移动端体验最好，但管理后台密度不足是硬伤。
